# Ontology 化 AI 工程方法论文档 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将用户现有的“流程镜像型 Ontology”方法，重构为以高价值业务决策、数据产品、预测模型、动作闭环和用户采用为核心的可执行工程方法论，并沉淀为两份后续研究资料。

**Architecture:** 文档分为两层。第一层解释 Ontology 化 AI 的总工程链路、每阶段的输入/动作/工具/产物/验收标准和常见失败模式；第二层专门解释散乱文件与多源资料如何被组织为可复用、可测试、可增量、可观测的数据产品。两份文档共同使用“官方事实 / 方法论推断 / 推荐实践”三类证据标签，并将未决风险转为检查项。

**Tech Stack:** Markdown、Mermaid、Palantir 官方 Foundry/AIP 文档链接、AI FDE/Document Intelligence 官方能力说明、开放 Agent 框架官方文档。

## Global Constraints

- 使用中文回复和中文文档。
- 不把静态 Ontology 描述误写成预测模型；明确预测需要时间、标签、特征、验证、部署和反馈。
- 对 Palantir 没有公开的现场操作细节，必须标注为“合理推断”或“推荐实践”，不能冒充官方事实。
- 数据管道文档必须覆盖结构化数据、非结构化文件、重复/冲突来源、版本、质量、增量、权限、血缘和反馈。
- AI FDE 的结论必须区分：官方公开能力、是否开源的公开证据边界、以及可替代的开源组合方案。
- 文档必须提供可执行指令、输入/输出、验收标准和失败处理，不只提供概念解释。

### Task 1: 诊断“Ontology 镜像化但没有预测能力”的根因

**Files:**
- Create: `wiki/10-Ontology预测能力诊断.md`

**Interfaces:**
- Consumes: 用户描述的原有流程镜像方法；官方 Ontology 核心概念、用例生命周期、数据管道和模型目标文档。
- Produces: 静态镜像、分析模型、预测系统、优化/执行系统之间的能力边界；供应商延误的最小完整闭环；根因检查清单。

- [ ] **Step 1: 定义四种模型形态**

  写清楚：
  - 描述模型：回答“世界是什么”；
  - 分析模型：回答“发生了什么/为什么”；
  - 预测模型：回答“将发生什么/何时发生”；
  - 决策/优化模型：回答“应该怎么做/采取动作后结果如何”。

- [ ] **Step 2: 对供应商延误建立输入—预测—动作闭环**

  至少覆盖：事件时间、预测时点、供应商/订单/交付对象、承诺日期与实际日期、先行信号、标签、模型、阈值、告警动作、人工反馈和实际结果。

- [ ] **Step 3: 写入故障诊断清单**

  每一项包含“问题、检测方式、合格标准”：无时间维度、无历史标签、只有结果没有过程信号、对象关系没有可计算特征、没有模型生命周期、没有回写动作、没有反馈数据、没有成本/收益指标。

- [ ] **Step 4: 用 Mermaid 画出镜像型 Ontology 与闭环型 Ontology 的差异**

  验收：读者能一眼看出 Ontology 不是预测引擎本身，而是预测所需上下文、模型、动作和反馈的运营承载层。

### Task 2: 编写 Ontology 化 AI 总方法论

**Files:**
- Create: `wiki/11-Ontology化AI工程方法论.md`

**Interfaces:**
- Consumes: 用户给出的 12 步工程链路；现有 `wiki/01-端到端工程方法.md`；官方用例生命周期、方案设计、角色、治理、Ontology、应用构造、AIP 和 DevOps 文档。
- Produces: 可直接执行的阶段化手册，包含阶段目标、进入条件、工作指令、输入、输出、角色、技术、验收门和失败处理。

- [ ] **Step 1: 固化工程总原则**

  说明“业务决策优先、数据产品先于 AI、Ontology 是运营 API、动作优先于聊天、反馈写回、渐进自动化、权限和质量前置”。

- [ ] **Step 2: 为每个阶段建立统一模板**

  每个阶段必须有：
  - 目标；
  - 输入；
  - 执行指令；
  - 参与角色；
  - 工具/技术；
  - 产物；
  - 进入下一阶段的验收标准；
  - 典型失败模式；
  - 需要向客户提问的问题。

- [ ] **Step 3: 详细展开 12 个阶段**

  覆盖：高价值决策、真实工作流观察、用户/输入/决策/动作、对象关系状态权限、数据接入与治理、数据产品、Ontology 映射、规则/模型/LLM/Agent、应用嵌入、动作和反馈、评估运营、产品化复制。

- [ ] **Step 4: 增加供应商延误端到端示例**

  从订单和供应商对象开始，经过数据管道、预测特征、模型推理、风险对象、告警工作流、人工确认、采购动作和结果反馈，形成一条完整示例。

- [ ] **Step 5: 增加客户协作与摩擦处理章节**

  采用“官方角色机制 + 合理推断”标签，覆盖领域负责人、工作流负责人、产品负责人、SME、数据/Ontology/应用团队、治理委员会、培训和支持。

- [ ] **Step 6: 增加 AI FDE 章节**

  说明 AI FDE 的公开能力、权限/上下文/工具/分支/CI 闭环；明确官方资料没有证明其开源，给出可替代的开源组合而不是声称存在一个等价单品。

### Task 3: 编写数据产品与散乱资料管道方法论

**Files:**
- Create: `wiki/12-数据产品与散乱资料管道方法论.md`

**Interfaces:**
- Consumes: 现有 `wiki/02-数据连接与集成.md`；官方 Pipeline、Data Connection、Data Expectations、Data Health、Media Sets、AIP Document Intelligence、媒体到 Ontology 文档。
- Produces: 从散乱文件/表格/API 到可信数据产品的可执行 SOP，以及供应商交付风险数据产品示例。

- [ ] **Step 1: 定义数据产品的生产契约**

  契约至少包含：业务目的、粒度、主键、时间语义、来源、刷新、质量、权限、血缘、版本、SLO、使用者、下游动作和反馈字段。

- [ ] **Step 2: 建立散乱资料盘点与分层流程**

  分为资料注册、来源归属、版本识别、文档/表格分类、内容抽取、结构化中间层、规范化实体层、Ontology 输出层；明确不确定和冲突资料不能静默合并。

- [ ] **Step 3: 建立非结构化文件处理流水线**

  覆盖 Media Set、原文保留、OCR/布局 OCR/VLM 抽取、Markdown/JSON、页码和 bounding box 证据、chunking、embedding、人工确认、批量 Python transform 和增量策略。

- [ ] **Step 4: 建立重复与冲突处理规则**

  处理同一事件多份文档、版本覆盖、字段冲突、日期冲突、供应商别名、单位差异、来源可信度、时间有效性和人工裁决；每条标准化记录保留来源证据。

- [ ] **Step 5: 建立质量控制与可观测性**

  通过 schema、主键、唯一性、完整性、时序、范围、业务规则、抽取置信/人工复核、数据期望、Data Health 和失败队列控制质量。

- [ ] **Step 6: 建立增量、回放、修订和反馈机制**

  明确新文件只处理新增项、文档修订重新处理受影响项、规则/prompt/模型改变可重跑、失败文档可单独重试、下游对象可追溯到原始页码和版本。

- [ ] **Step 7: 增加供应商延误数据产品模板**

  定义供应商、合同、订单、订单行、承诺交付、发货、运输、收货、异常、变更通知、历史延误标签、风险特征和预测输出的结构。
