# Palantir 风格的端到端工程方法

## 1. 总体判断

Palantir 的平台不是“先建数据仓库，再单独做 BI，再单独做 AI”的工具集合，而是一个围绕企业决策的交付系统。官方架构把 AIP、Foundry 和 Apollo 分别定位为生成式 AI、数据运营和持续交付平台；Ontology 位于其中心，把数据、逻辑、动作和安全放到同一语义与执行平面上。

因此，正确的工程主线不是“先选产品”，而是：

```text
业务结果
  -> 决策/动作需求
  -> 数据基础
  -> Ontology 语义与权限
  -> 规则/函数/模型/Agent
  -> 分析与工作流应用
  -> 人机协同执行
  -> 观测、反馈、评估
  -> 版本化产品交付
  -> 规模化复制与持续改进
```

## 2. 项目时序总表

| 工期节点 | 关键任务 | 主要技术 | 原理 | 交付物 / 通过标准 |
|---|---|---|---|---|
| T0 立项 | 选用例、确定业务结果、建立赞助与团队 | Use case intake、Program team、SteerCo | 用例按用户能力和业务结果定义，而非按数据源或模型定义 | 用例章程、价值假设、负责人、用户群、KPI |
| T1 发现 | 访谈用户，提炼决策和动作 | 功能需求模板、用户旅程 | 把模糊需求变成“谁在什么界面基于什么输入做什么决策/动作” | 功能需求、利益相关者、当前痛点、验收指标 |
| T2 设计 | 设计对象、关系、状态、数据丰富、界面 | Solution Design、Object model、lifecycle diagram | 先设计决策语义，再选择 Pipeline、Ontology、Workshop、Quiver 等实现 | 方案图、对象模型、生命周期、数据丰富清单、界面意图 |
| T2.5 基础 | 建项目、组、角色、权限、数据治理和支持机制 | Projects、Groups、IdP、markings、retention、audit | 权限和治理是数据生命周期的一部分，不是上线前补丁 | 项目结构、角色矩阵、敏感数据策略、审计方案 |
| T3 接入 | 连接外部系统，把原始数据可靠同步进来 | Data Connection、batch/stream/CDC/media、agent runtime | 原始层尽量保真，变化通过分支和版本化管道管理 | Source、凭证、运行时、同步任务、原始数据集 |
| T3.5 数据产品 | 清洗、连接、增量化、质量检测、调度 | Pipeline Builder、Code Repository、expectations、Data Health | 数据管道是软件；可重复、可测试、可观察、可维护 | 质量数据集、数据血缘、期望检查、调度、健康监控 |
| T4 语义建模 | 把数据映射为对象、属性、链接和对象集 | Ontology Manager、object/link types、shared properties | 用业务对象和关系承载跨源语义，消除应用对数据表细节的耦合 | Ontology schema、主键/基数、对象集、权限模型 |
| T4.5 业务逻辑 | 把规则、状态变化、外部调用和人工编辑变成可审计动作 | Action types、Functions、Logic、Automate、webhooks | “动词”与“名词”同样重要；动作是受权限和条件约束的事务 | 动作定义、规则、函数、通知、回滚/取消策略 |
| T5 探索 | 先用分析验证对象模型、指标、因果假设和用户视角 | Contour、Quiver、Code Workbook、Code Workspaces、Notepad | 分析不是终点，而是方案验证和决策知识生产环节 | 分析结果、指标、仪表盘、待建字段/对象/模型清单 |
| T5.5 模型 | 训练或接入模型，建立评估和模型治理 | Model Adapter、Modeling Objective、MetricSet、batch/live deployment | 模型被当作可版本化生产资产，而不是一次性 notebook 输出 | 模型适配器、提交、评估、发布、部署、指标看板 |
| T6 应用 | 围绕用户决策构造读、分析、写、协作界面 | Workshop、Slate、Object Views、Carbon、OSDK | 应用调用同一 Ontology API，动作和权限保持一致 | 可用应用、对象视图、表单、嵌入分析、端到端流程 |
| T6.5 AI | 在有权限的上下文中使用 LLM、Logic、Agent 和工具 | AIP、AIP Logic、Chatbot Studio、Agents、Evals | LLM 负责理解和推理，Ontology 提供受控上下文、工具和动作 | AI 函数、工具清单、评估集、人工审批、调用/令牌观测 |
| T7 运营化 | 让事件、计划、动作和反馈持续运行 | Automate、streaming、schedules、audit、Data Health、model metrics | 生产系统必须能观察、解释、重试、升级、回放和干预 | 运行手册、告警、SLO、支持队列、反馈数据 |
| T8 交付 | 把管道、Ontology、模型、应用和连接作为产品发布 | Branch/PR、Foundry DevOps、Marketplace、release channels | 交付单位是完整能力包，不是孤立代码或单个仪表盘 | 产品包、版本、依赖、渠道、安装、升级和回滚方案 |
| T9 扩展 | 通过新用例复用资产、扩大用户和生态 | Product fleet、adoption phases、governance reviews | 每个用例沉淀可复用对象、逻辑、界面和工程能力 | 复用目录、季度组合评审、采用率、ROI、下一轮路线图 |

## 3. 关键工程原则

### 3.1 从“用户决定什么”而不是“我们有什么数据”开始

官方用例生命周期把用例定义为在限定时间内为一组用户提供新能力并产生可度量结果的工作，而不是“接入某数据源”或“使用某个 ML 模型”。需求句式应同时包含用户类型、界面、决策、输入和动作。

### 3.2 先建可用基础，再扩大决策空间

官方建议先做稳健高效的数据管道、平衡且有代表性的 Object model、初始界面和决策指导；随后再把数据科学、模型驱动工作流、数字孪生和场景规划接入。这样可以先让用户得到价值，也避免模型或 UI 建在不稳定的数据和语义上。

### 3.3 数据丰富优先放到数据层，交互状态才放到动作层

可复用、需要过滤/聚合/分析的指标，尽量在数据产品或 Ontology 属性中提前计算；只依赖用户当前输入、且必须实时变化的结果，才在应用函数或动作中计算。前者更易复用、性能更稳定，后者更适合交互性但会增加页面计算和重复逻辑。

### 3.4 把决策闭环写回系统

分析、模型和 Agent 不能只输出报告或文本。用户的重新分配、批准、解决、升级、调整参数等动作应通过 Ontology action 进入受治理的数据流，以形成新的事实、反馈标签、模型输入和运营记录。

### 3.5 把质量、权限、血缘、审计、版本放进同一条生产路径

一个数据集即使数值正确，如果权限传播错误、上游变化不可解释、没有失败通知或无法回滚，也不是可交付的数据产品。Foundry 文档把数据期望、分支/PR、数据健康、权限标记、血缘和审计全部放进生产体系。

## 4. 每个阶段的“过门”检查

### T0/T1：价值门

- 是否明确用户、当前决策、痛点、动作和结果，而不是泛泛地说“做 AI 平台”？
- 是否有可衡量的业务指标、基线和目标？
- 是否有领域负责人、产品负责人、工作流负责人、应用负责人和数据/Ontology/模型开发者？

### T2/T2.5：方案与治理门

- 对象模型是否表达真实实体和事件，还是把源表机械改名？
- 是否说明核心对象、派生对象、用例编辑对象、链接基数和生命周期？
- 是否完成数据分类、目的限制、保留期限、角色组和下游引用策略？

### T3/T3.5：数据生产门

- 原始同步是否可重试、可监控、可追溯？
- 管道是否有小而清晰的 transform、显式类型、测试、期望、分支和发布流程？
- 是否根据规模和时延选择 batch、incremental、stream 或 CDC？

### T4/T4.5：语义与行为门

- 对象、属性、链接、动作、函数和权限是否能共同解释一个用户流程？
- 动作是否是可授权、可验证、可审计的事务？
- 逻辑是否尽量复用，避免把相同业务规则散落在多个应用里？

### T5/T5.5/T6：可用性门

- 用户是否能从对象/集合出发理解上下文，并完成动作？
- 分析结果是否支持发现、验证和决策，而不是只读报表？
- 模型是否有不可变提交、评估、发布、部署和指标，而不是“模型文件已上传”？
- AI 是否只使用所需上下文和工具，并能通过人工审批或权限边界控制高风险动作？

### T7/T8/T9：生产与规模门

- 是否有失败处理、重试、告警、审计、运行手册和责任人？
- 是否能将完整资源包版本化、分渠道发布、按维护窗口升级？
- 下一用例能否复用对象、函数、动作、模型、界面或部署模板？

## 5. 常见反模式

1. **从技术资产立项：**“我们有 ERP 数据，做一个模型。”应改成“哪个角色要做什么决策，模型是否真的改变该决策？”
2. **把需求锁死为页面：**先画 20 个页面再讨论业务，容易把用户目标缩窄为 UI。先写决策和动作，再选 Workshop、Slate、Object View、Quiver 或 Carbon。
3. **把 Ontology 当作表目录：**只建对象和属性而没有动作、生命周期、权限和反馈，无法产生运营闭环。
4. **一开始就追求全量实时：**实时链路复杂度和成本很高；先做可验证的 batch，再按变化量、时延和决策价值升级到 incremental/stream/CDC。
5. **把模型当 notebook 文件：**没有适配器、模型目标、评估、发布和部署，无法进入应用或动作。
6. **把敏感数据安全放到最后：**标记会沿血缘传播；越晚治理，迁移、重建和证明成本越高。
7. **把交付理解成上线一个应用：**数据连接、管道、Ontology、模型、动作、权限和应用必须作为一个可安装、可升级产品考虑。
