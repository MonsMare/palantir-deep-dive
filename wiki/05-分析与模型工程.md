# 分析与模型工程

## 1. 分析的定位

Foundry 分析工具共享 Ontology、数据安全、血缘和治理。分析不止读取数据：洞察可以进入对象、指标、动作和应用，成为决策闭环的一部分。

| 工具 | 主要工作 | 进入工程闭环的作用 |
|---|---|---|
| Contour | 面向数据集的表格探索、路径、聚合、可视化和变换 | 快速检查数据、定义指标、验证管道结果 |
| Quiver | 对象/时间序列探索、关系导航、无代码变换、参数化仪表盘 | 以对象为中心解释问题、形成可嵌入分析 |
| Code Workbook | Python/R/SQL、数据变换、模型和模板 | 交互式探索与可发布的数据/模型资产 |
| Code Workspaces | JupyterLab、RStudio、VS Code | 熟悉 IDE 中的分析、模型、应用和流程开发 |
| Notepad | 动态分析、解释、媒体、报告和模板 | 将分析结果转化为可阅读、可协作的业务知识 |
| Fusion / Forms | 表格、人工输入、校验和工作流集成 | 把人工修正和运营输入写回系统 |

Code Workspaces 与 Foundry 安全、分支、调度和资源管理集成，但单节点更适合模型和交互探索；大规模管道、连接和流处理仍应使用 Pipeline Builder、代码仓库和 Streaming。

## 2. 模型工程生命周期

### 2.1 选择建模工具

根据规模、模型类型、语言、团队习惯和运行方式，在 Code Workbook、Code Workspaces、代码仓库、Foundry 训练、外部模型服务之间选择。先明确模型要改变哪个决策，而不是先决定使用哪种算法。

### 2.2 统一模型工件与适配器

Foundry 将模型拆成：

- **Model artifact：**权重、参数、容器、凭据或模型文件。
- **Model adapter：**加载、初始化、输入输出 API 定义和 `predict()` 推理逻辑。

适配器使平台以相同方式消费 Foundry 内训练、外部文件、容器化或外部托管的模型。它隔离模型内部实现与平台调用契约，是模型复用和可替换性的关键。

### 2.3 用 Modeling Objective 管理问题

Modeling Objective 是围绕一个运营问题组织数据源、元数据、模型版本、评估和发布的项目。模型提交不可变，类似代码 PR；经过评估和审核后形成可部署版本。这样模型从“文件”变为有上下文、有责任、有历史的生产资产。

### 2.4 评估、发布、部署

生产路径通常是：

```text
模型提交 -> 自动/自定义评估 -> 对比指标和数据切片
         -> 审核 -> Release / tag
         -> batch 或 live deployment
         -> 模型指标、推理历史和业务结果监控
```

Batch deployment 对输入数据集运行并生成输出数据集，适合大规模离线推理；Live deployment 以受认证的 REST endpoint 提供低延迟推理，可在不停止服务的情况下更新并保持版本血缘。发布渠道和部署自动跟随受治理的模型版本。

### 2.5 把模型绑定到 Ontology

模型通过函数、动作、Workshop、Slate、场景分析或自动化进入业务流程。模型输出不应停留在一个孤立预测表中，而应转化为对象属性、建议、风险、排序或受控动作输入，并与用户反馈和真实结果关联。

## 3. 外部模型接入的安全边界

外部托管模型可以作为 Foundry 中的模型代理，接入 SageMaker、Vertex AI、OpenAI 等服务。需要模型适配器、连接详情、凭据和 Foundry 出口策略。出口策略明确允许什么数据离开 Foundry；凭据应加密保存。当前官方文档提示外部模型不支持建模目标中的批处理部署和自动模型评估，批处理场景需要通过 Python transform 处理，这应在方案设计时明确。

## 4. 模型验收指标

- 业务：是否改善决策速度、质量、成本、风险或资源配置。
- 技术：准确率、召回率、校准、延迟、吞吐、资源使用和失败率。
- 数据：训练/评估/生产分布、漂移、缺失、泄漏和数据新鲜度。
- 运营：用户采纳、人工覆盖率、建议采纳率、误报/漏报、动作完成率。
- 治理：模型版本、输入输出、权限、外部调用、审计、解释和回滚。
