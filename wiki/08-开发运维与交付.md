# 开发运维与产品交付

## 1. 开发纪律

Foundry 文档明确把管道开发视为软件开发：

- 项目按职责划分，使用有意义的目录、名称和文档。
- 不在个人文件夹中长期生产化工作。
- 主分支受保护，改动通过分支、测试、代码评审和 PR 合并。
- 提交信息说明为什么改，而不只是改了什么。
- 共享库、依赖和环境配置纳入版本控制。
- 通过数据期望、单元测试、构建历史和 Data Health 发现回归。

同样的原则适用于 Ontology、Functions、Logic、模型、应用模块和 Agent 定义。

## 2. 生产运维

进入维护模式前应明确：管道范围、输出、交付时间、构建时机/周末窗口、理想频率和过期阈值。维护者需要数据访问权、仓库/构建/血缘/Data Health 能力以及系统架构知识。

运行手册至少包含：

- 上游、下游和负责人。
- 新鲜度、延迟、质量、可用性和成本 SLO。
- 构建失败、数据迟到、schema 变化、权限错误、外部服务失败的处置。
- 重跑、回滚、重放、补数和人工干预方案。
- 模型/Logic/Agent 的版本、评估、发布和回滚策略。
- 告警升级和用户沟通方式。

## 3. Foundry DevOps 与 Marketplace

Foundry DevOps（官方中文页面当前标注为有限测试）允许把任意组合的 Ontology、AI 模型、管道、连接、自动化和端到端用例资源打包成产品，自动管理版本和依赖，通过 release channel 标签控制哪些安装接收更新，并管理安装舰队。

它支持四类交付：

1. 产品分发：将数据产品发布给组织内外安装者。
2. 生态系统搭建：为客户、子公司或部门按其输入数据安装同一产品。
3. 发布管理：把开发环境映射为安装，配置维护窗口和升级渠道。
4. 用例引导：安装既有产品作为新用例的起点。

因此，交付单位从“应用上线”提升为“可安装的能力包”。必须考虑哪些资源由产品拥有、哪些允许最后一公里定制、输入数据如何注入、依赖如何解析、升级如何兼容以及失败如何恢复。

## 4. Apollo 与持续交付

官方架构中心将 Apollo 定位为支撑 AIP 和 Foundry 的持续交付平台。它使大量微服务和资产能够在异构环境中持续发布、升级和保持高可用。即使当前项目只使用 Foundry DevOps，也应按同一思想设计：小版本、自动验证、可观测发布、维护窗口、渠道和回滚。

## 5. 交付验收

- 产品包包含所需数据连接、管道、Ontology、模型、应用、Logic 和权限配置。
- 所有资源有版本、依赖和责任人。
- 安装前有输入检查、环境检查、权限和出口策略检查。
- 新版本有测试结果、评估结果、迁移说明和兼容性说明。
- 支持灰度/渠道发布、维护窗口、失败告警和回滚。
- 安装后可从数据健康、模型指标、用户行为和审计日志证明产品在运行。
