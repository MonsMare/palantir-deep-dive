# 用例开发与应用构造

## 1. 从需求到解决方案

Palantir 的用例开发不是由应用开发者单独画页面，而是一个由业务、数据、Ontology、模型和应用共同完成的决策工程。

### 需求句式

```text
[用户类型] 在 [界面] 基于 [决策输入] 做出 [决策]，并执行 [动作]
```

例如：运营分析员查看告警收件箱，基于优先级、航线和组织影响对告警分类，然后重新分配、解决或升级告警。这个句式同时暴露用户、界面、数据输入、决策和动作，避免只得到“做一个告警看板”。

### 方案设计四件套

1. **Object model：**核心对象、派生对象、用例编辑对象、属性、链接、主键和基数。
2. **Lifecycle diagram：**对象状态、状态转移、动作触发条件和可用动作。
3. **Data enrichment list：**新增的对象级概念、属性级指标、规则、模型和人工输入。
4. **Interface expectations：**直接操作、分析并记录、理解/汇报三类界面意图。

## 2. 工具选择原则

| 用户任务 | 默认工具 | 原因 |
|---|---|---|
| 围绕对象收件箱、筛选、详情和动作 | Workshop | 对象中心、低代码、动作/函数/权限天然集成 |
| 单个对象的上下文、关系、指标和工作流 | Object Views | 把对象作为工作入口，统一展示关联信息和动作 |
| 自由布局、响应式、复杂前端交互 | Slate | HTML/CSS/JS 与 Ontology 集成，适合定制界面 |
| 多对象、时间序列、交互式探索和仪表盘 | Quiver | 适合对象关系、时序、无代码变换和参数化分析 |
| 大规模工程代码、复杂数据和模型 | Code Repository / Code Workspaces | Git、环境、测试、Python/R/IDE 和工程化控制 |
| 文档、解释、分析叙事、模板报告 | Notepad | 把动态分析和业务说明放在同一交付物中 |
| 表格交互和人工输入 | Fusion / Forms | 保留熟悉的表格体验，并能连接数据集、对象和动作 |
| 组织级可复用应用/模块组合 | Carbon | 将工作空间、模块、权限和 YAML 配置组合交付 |
| 外部系统开发 | OSDK / Foundry APIs | 在平台外使用 Ontology 语义、权限和动作 |

## 3. 用例开发的工程节奏

1. 先做一条最小但完整的用户路径：输入 → 理解 → 决策 → 动作 → 结果记录。
2. 先用已有数据和轻量规则证明价值，再逐步加入模型和 Agent。
3. 先把动作和数据编辑设计成 Ontology action，再让不同应用调用同一动作。
4. 把用户反馈、人工修正、批准、驳回、升级和异常记录写回 Ontology。
5. 当流程稳定后，再提取通用模块、函数、对象视图和应用产品，供后续用例复用。

## 4. 为什么 Ontology 能降低应用成本

应用不必重复理解每个源系统的表、字段和连接方式。它面向对象、关系和动作；数据管道可以更换来源，模型可以替换版本，应用也可以从 Workshop 换成 Slate/OSDK，而业务语义、权限和行为契约仍保持稳定。这种解耦是 Palantir 所谓“共同基础上的复合效应”的主要来源。

## 5. 交付验收

- 用户能够从对象或对象集进入任务，不依赖开发者解释数据库结构。
- 关键动作有参数、校验、权限、确认、通知、审计和错误处理。
- 应用、分析、模型和 Agent 读取的是同一 Ontology 语义。
- 任何重要决定都有可追踪的输入、推荐、用户动作和结果。
- 业务指标能与用户采用率、流程时长、准确率、异常率等产品指标关联。
