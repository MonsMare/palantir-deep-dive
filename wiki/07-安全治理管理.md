# 安全、治理与管理

## 1. 安全的设计位置

Foundry 的安全不是一个登录模块，而是身份认证、授权、项目/组织/组、数据集行列控制、权限标记、血缘传播、对象和动作权限、网络出口、审计和基础设施防御的组合。安全必须在 T2 方案设计和 T3 数据接入前完成主要决策。

## 2. 推荐的项目与权限结构

官方数据基础示例采用三层项目：

```text
Flight Control   -> 数据源与原始/清洗数据
Flight Delays    -> 可复用转换与业务数据产品
Aviation         -> Ontology、应用、分析和运营流程
```

每个项目按角色建立组，并通过项目引用让下游使用上游输出，而不必直接开放原始项目。实践中可对应为：Raw / Clean / Product / Ontology-App 分层；但具体项目边界应由数据敏感性、组织责任和复用方式决定。

## 3. 敏感数据治理

权限标记实现强制访问控制。用户即使有项目所有者权限，也不能绕过敏感标记。标记可沿血缘传播，因此应在早期识别 PII、财务、健康、任务敏感和出口受限数据。

推荐顺序：

1. 建立数据治理委员会、数据所有者、隐私/法律 SME 和项目负责人。
2. 在导入前明确处理目的、最小化原则、保留/删除规则和跨境/外发要求。
3. 使用扫描器和人工审查识别敏感字段，分配标记和允许组。
4. 在分支中验证删除、脱敏或聚合不会继续传播敏感字段。
5. 通过 PR 和受保护分支发布，并用血缘、模拟和审计证明结果。

## 4. 管理与组织机制

Foundry Program team 是业务和技术的集中枢纽，负责数据管理、Ontology/技术管理、项目管理、用例开发和治理。组织能力比单个页面或 API 更决定长期成效。

治理节奏包括：

- **季度 SteerCo：**审视在产、开发中和潜在用例的价值、成本、用户、平台和优先级。
- **月度路线图/开发评审：**审视业务案例、计划变化、阻塞和排序。
- **双周 Sprint 计划：**确认交付、未完成工作、容量、验收条件和任务分工。
- **每日短会：**同步数据、Ontology、用例和治理阻塞。
- **持续访问/数据权限审查：**使用 IdP 组，减少直接给个人授权。
- **项目创建审查：**由中心团队控制项目、组、角色和安全基线。
- **持续支持：**从早期项目团队支持，逐步建立专门的内部 Foundry 支持团队。

## 5. Adoption 分阶段

早期阶段通常只有少量生产用例和少量用户，应优先建立项目负责人、用例团队、平台/数据治理团队，并控制用例数量和类型。随着采用扩大，需要形成中心化的架构、Ontology、数据、平台、支持和培训能力，避免每个项目都重复建设。

## 6. 审计与责任

审计日志不仅记录“谁登录了”，还应能回答：哪个用户/Agent、在什么资源和上下文中、读取或修改了什么、通过哪个服务和调用链、产生了什么后果。AI 时代尤其需要记录 Agent 的工具调用、动作参数、模型版本、评估版本和人工介入。
