# Ontology 化 AI 工程方法论：可执行版

## 1. 这套方法要改变什么

旧方法通常是：

```text
建 Ontology
→ 接大模型
→ 做聊天机器人
```

这会把 Ontology 做成知识展示层，把 LLM 做成问答层，缺少真正的业务结果。

新的方法是：

```text
找到高价值业务决策
→ 深入观察真实工作流
→ 明确用户、输入、决策和动作
→ 设计对象、关系、状态和权限
→ 接入并治理数据
→ 建成可复用数据产品
→ 将数据映射到 Ontology
→ 将规则、模型、LLM 和 Agent 接入 Ontology
→ 嵌入用户每天的工作流
→ 让动作和反馈回写系统
→ 通过评估和运营持续改进
→ 产品化并复制到更多部门
```

Palantir 官方也强调先建立数据资产和决策指导，再扩展到模型驱动的运营工作流。[开发排序](https://www.palantir.com/docs/zh/foundry/use-case-life-cycle/sequencing-development)

## 2. 五条总原则

### 原则一：先问“哪个决策需要改善”

不要从“我们有哪些数据”或“我们可以用哪个模型”开始。

### 原则二：数据产品先于预测模型

如果数据没有稳定粒度、主键、时间语义、质量规则和血缘，模型只是把数据问题隐藏起来。

### 原则三：Ontology 是运营 API，不是数据库目录

Ontology 必须同时描述对象、关系、状态、权限、动作和反馈。

### 原则四：AI 先建议，再执行

通过人工确认、动作白名单和逐步自动化建立信任。

### 原则五：每个动作必须产生反馈

没有动作结果，就没有可靠的模型评估、阈值优化和持续学习。

## 3. 阶段 0：建立项目边界和责任体系

### 目标

确定一个具备业务价值、用户边界和可落地范围的用例。

### 执行指令

1. 指定领域负责人，负责 ROI 和战略优先级。
2. 指定用例负责人，负责进度、协调、权限和用户采用。
3. 指定产品负责人，负责功能路线图和用户反馈。
4. 指定领域 SME，负责业务语义、例外和当前痛点。
5. 指定数据、Ontology、模型和应用负责人。
6. 确认业务赞助人和冲突升级路径。
7. 规定项目不解决什么，防止范围无限扩张。

### 必须采集

- 业务背景；
- 当前流程；
- 目标用户；
- 目标决策；
- 当前 KPI；
- 预期收益；
- 关键风险；
- 数据和系统边界；
- 业务负责人和技术负责人。

### 产物

- 用例章程；
- 价值假设；
- 角色矩阵；
- 范围边界；
- 项目治理节奏。

### 通过标准

- 不能只写“建设 AI 能力”；
- 必须能说出具体用户和具体业务结果；
- 必须有能对结果负责的领域负责人。

## 4. 阶段 1：找到高价值业务决策

### 目标

从业务结果倒推最值得改造的决策节点。

### 执行指令

对每一个候选流程填写：

```text
流程名称：
目标用户：
最终业务结果：
当前决策：
决策频率：
决策时限：
决策错误的成本：
决策延迟的成本：
当前使用的系统：
当前人工工作量：
可自动化动作：
可形成反馈的数据：
```

### 优先级评分

用 1–5 分评估：

- 业务价值；
- 决策频率；
- 当前损失；
- 数据可获得性；
- 用户采用可能性；
- 可复用性；
- 权限和合规复杂度；
- 预测/优化改善空间。

优先选择“价值高、边界清晰、有真实用户、有数据但还没有被有效利用”的流程。

## 5. 阶段 2：深入观察真实工作流

### 目标

把业务人员的隐性判断、例外处理和跨系统操作变成可建模的事实。

### 访谈指令

不要只问“你们怎么做”，而要要求用户还原最近一次真实事件：

1. 事情什么时候发生？
2. 当时你首先看到什么？
3. 你打开了哪些系统和文档？
4. 哪些数据是必须的？
5. 哪些数据不可信或缺失？
6. 你如何判断优先级？
7. 哪些情况会改变判断？
8. 你会咨询谁？
9. 你最终做了什么动作？
10. 动作结果记录在哪里？
11. 如果结果不好，你如何补救？

### 观察重点

- 人工复制和粘贴；
- Excel 中的隐含规则；
- 邮件和聊天中的事实；
- 不同部门对同一对象的不同定义；
- 依赖资深员工经验的判断；
- 例外和升级路径；
- 用户真正愿意承担的自动化程度。

### 产物

- 当前工作流图；
- 决策点清单；
- 用户旅程；
- 例外清单；
- 数据来源清单；
- 当前系统痛点清单。

## 6. 阶段 3：把需求写成用户—界面—决策—输入—动作

### 指令

每条功能需求必须写成：

```text
[用户类型] 在 [界面]
基于 [决策输入] 做出 [决策]
并执行 [动作]
```

例如：

```text
采购经理在供应商风险收件箱中，
基于供应商历史准时率、订单状态、运输事件和当前库存，
判断订单是否存在未来 7 天延误风险，
并选择加急、改派、调整库存或升级审批。
```

### 禁止写法

- “建设供应商数据平台”；
- “实现供应商大模型”；
- “做一个供应链驾驶舱”；
- “把所有数据放进 Ontology”。

这些是技术或范围描述，不是功能需求。

### 工具选择

- Workshop：对象中心运营工作流；

- OSDK：外部系统和专业应用；
- Automate：事件/计划驱动自动化。

## 8. 阶段 5：建立安全与数据治理边界

### 指令

在数据接入前完成：

1. 数据分类；
2. 目的和用途；
3. 敏感字段；
4. 用户组；
5. 项目角色；
6. 行/列/对象权限；
7. 网络出口；
8. 保留和删除；
9. 审计要求；
10. 外部模型和 API 限制。

权限尽量绑定 IdP 组，不直接给个人授予生产权限。[安全总览](https://www.palantir.com/docs/zh/foundry/security/overview)

## 9. 阶段 6：数据接入与来源登记

### 每个数据来源必须登记

```text
来源名称：
业务所有者：
技术所有者：
来源系统：
数据粒度：
主键：
事件时间：
观察时间：
刷新频率：
历史保留：
权限：
敏感级别：
质量问题：
下游用途：
```

### 技术选择

- Batch：周期性完整同步；
- Incremental：只处理新增或变化；
- CDC：捕获数据库变化；
- Streaming：低延迟事件；
- Media Set：文档、图片、音频和视频；
- External Transform/Function：不常规的外部系统。

## 10. 阶段 7：建设数据产品

数据产品不是“加工后的表”，而是具有生产契约的业务资产。

每个数据产品必须定义：

- 业务用途；
- 粒度；
- 主键；
- 时间语义；
- 来源和血缘；
- 更新方式；
- 质量规则；
- 权限；
- SLO；
- 使用者；
- 下游对象/模型/动作；
- 失败和回放方案。

数据管道应使用分支、PR、质量检查、数据期望和健康监控。[数据期望](https://www.palantir.com/docs/zh/foundry/maintaining-pipelines/define-data-expectations)

## 11. 阶段 8：Ontology 建模

### 建模顺序

1. 核心对象：稳定的业务实体和事件；
2. 关键关系：对象之间的业务关系；
3. 派生对象：由多个对象和指标计算的概念；
4. 用例对象：告警、工单、审批、评论、计划；
5. 状态机：对象生命周期；
6. 动作：用户和系统如何改变状态；
7. 函数：复杂逻辑、模型和外部调用；
8. 权限：谁能看、调用和修改什么；
9. 对象视图和应用：用户如何消费。

### 建模验收

- 对象能被业务人员解释；
- 属性有来源和时间语义；
- 主键稳定；
- 链接有方向和基数；
- 派生对象可重复计算；
- 动作有参数、条件、权限和审计；
- 应用不依赖源表细节；
- 模型和 Agent 可以使用对象、关系和动作。

## 12. 阶段 9：接入规则、模型、LLM 和 Agent

### 选择顺序

1. 规则：确定性逻辑；
2. Function：复杂业务计算和外部调用；
3. 传统 ML：结构化预测和分类；
4. 优化器：资源、路径、库存、排产；
5. LLM Logic：抽取、分类、总结、解释和结构化生成；
6. Agent：动态规划、多工具和复杂任务。

### AI 输入契约

```text
允许读取的对象：
允许读取的属性：
允许调用的函数：
允许执行的动作：
必须返回的结构：
必须提供的证据：
失败状态：
人工审批点：
审计字段：
```

AI FDE、AIP Logic 和 Agents 都应通过受控上下文、工具权限、分支、预览、评估和审查进入生产。[AIP 架构](https://www.palantir.com/docs/foundry/architecture-center/aip-architecture)

## 13. 阶段 10：嵌入用户工作流

### 设计原则

不要让用户重新学习一套抽象的数据系统，而应把能力放入原有工作任务：

```text
我的任务
→ 相关对象
→ 上下文和证据
→ 推荐和预测
→ 可执行动作
→ 审批/覆盖
→ 结果回写
```

### 上线顺序

1. 统一视图；
2. 分析和搜索；
3. 推荐和预测；
4. 人工确认动作；
5. 低风险自动化；
6. 跨部门协同；
7. 复制到邻近工作流。

## 14. 阶段 11：运营、评估和反馈

### 必须监控四类指标

#### 数据指标

- 新鲜度；
- 完整性；
- 唯一性；
- 质量检查失败率；
- 来源覆盖率。

#### 模型/AI 指标

- 准确率/召回率/误报/漏报；
- 预测提前量；
- LLM 结构化输出合格率；
- 工具调用失败率；
- token 和计算成本；
- 响应延迟。

#### 工作流指标

- 处理时长；
- 告警关闭率；
- 人工覆盖率；
- 审批时长；
- 动作失败率。

#### 业务指标

- 避免损失；
- 成本下降；
- 收入提升；
- 风险减少；
- 用户采用率。

## 15. 阶段 12：产品化和复制

当对象、数据产品、函数、动作、模型和应用稳定后，再打包成可复制产品。

交付包应包含：

- 连接；
- 管道；
- Ontology；
- 模型；
- Logic/Agent；
- 应用；
- 权限；
- 配置；
- 版本；
- 依赖；
- 安装参数；
- 升级和回滚；
- 运行手册。

## 16. 客户协作与摩擦处理指令

### 官方事实

Palantir 建议客户建立中心化 Foundry Program Team，逐步接管数据管理、Ontology 管理、用例开发、应用发布、用户培养和支持。[Foundry Program](https://www.palantir.com/docs/foundry/foundry-adoption/program-overview)

### 推荐实践

1. 不让技术团队单独定义业务语义；
2. 不让业务团队单独定义数据结构；
3. 对争议对象建立领域 Owner；
4. 对争议指标建立计算契约；
5. 对争议动作建立决策权限；
6. 用原型和数据证据处理争议；
7. 让原有团队看到系统如何减少工作，而不是只看到自动化风险；
8. 先让用户获得辅助能力，再逐步扩大自动化；
9. 为用户建立培训、支持和反馈机制；
10. 将采用率和业务结果纳入产品负责人的责任。

## 17. 你原方法的根本改变

旧问题不是“不够多地建 Ontology”，而是缺少以下四个闭环：

```text
时间闭环：过去状态 → 当前预测 → 未来结果
决策闭环：数据 → 判断 → 动作
学习闭环：预测 → 人工反馈 → 真实结果 → 再训练
采用闭环：系统能力 → 用户行为 → 业务结果 → 产品迭代
```

Ontology 是这些闭环的共同承载层，但预测、优化和学习必须由独立的数据产品、模型和反馈机制提供。
